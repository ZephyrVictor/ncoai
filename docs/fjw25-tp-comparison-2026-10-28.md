# fjw25 四卡与双实例推理对比（2026-10-28）

## 结论与适用范围

在本次固定工作负载下，**两套 TP=2 vLLM、每套 `MAX_NUM_SEQS=64`** 的合计吞吐为 2.197 完成请求/秒、1,125 输出 token/秒，比单套 TP=4、上限 64 高 **43.9%**；平均首 token 延迟从 34.21 秒降至 12.45 秒，p95 从 79.25 秒降至 45.27 秒。每组均为 160/160 成功。相同总活跃上限 64 的对照（双 TP2 各 32 对单 TP4 64），双实例吞吐仍高 12.2%，平均及 p95 首 token 延迟均较低。

这是预热后的**有限突发**：以 80 请求/秒发送 160 个请求，约 2 秒发完，再等全部排空；不是持续承载 80 完成请求/秒的证据。压测直连 vLLM，双实例按请求轮询分发，没有经过 LiteLLM、Chainlit 或浏览器。当前 Chat 的 LiteLLM 主备配置不负责将两个 TP2 副本均衡分流；若采用双实例，需要先接入并验收负载均衡、健康检查与故障切换。当前前端验收仍使用现有的单套 TP4/64 架构。

## 测试条件

- 服务器：`fjw25`，4 × RTX A6000，每卡 49,140 MiB；GPU 0/1 与 2/3 分别在同一 NUMA 域，无 NVLink。
- 模型：`models/Qwen3.8-27B`，BF16，权重 55,562,855,904 字节；vLLM 0.31.0，Torch 2.13.0+cu126。
- 共用设置：`MAX_MODEL_LEN=4096`、`MAX_NUM_BATCHED_TOKENS=8192`、`GPU_MEMORY_UTILIZATION=0.90`、prefix caching 开、CUDA graphs 开、`VLLM_USE_FLASHINFER_SAMPLER=0`。
- 预热：每个实例四次；启动和编译时间排除在表中。
- 请求：固定 seed 20261028，同一组 160 个提示，平均输入约 255 token；每请求强制输出 512 token，SSE 流式传输、关闭 thinking。双实例各分到 80 个请求。
- 客户端按绝对时间调度，无请求并发限流；实际发送跨度约 1.99 秒，发送延迟 p95 约 1–1.5 毫秒。所有组均校验 SSE 结束标记、usage 与 512 输出 token。

| 单套 TP4 | 32 | 160/160 | 133.70 | 1.197 | 613 | 54.73 / 108.21 | 79.77 / 131.92 | 20.42 |

单套 TP4 从 32 提到 64，完成吞吐增加 27.6%，首 token p95 缩短 26.8%，但单流平均生成速度从 20.42 降至 15.64 tok/s。两套 TP2 各 64 的合计活跃上限为 128，不等于单套 TP4 的 64；表中双 TP2 各 32 是总上限相同的比较。各组峰值运行/等待请求分别为 32/128、64/96、64/96、64/96、128/32；未观察到 KV cache preemption。GPU 显存峰值分别约每卡 43,409、43,939、TP2 两卡 44,383、43,949、44,131 MiB，均低于 49,140 MiB。

TP4 的四张卡共同保存一个模型的分片，并在每一批推理中通信；只有一个请求队列和一个 `MAX_NUM_SEQS` 上限。双 TP2 是每两张卡独立保存一套模型的分片、运行一套完整 vLLM 引擎；请求只能落在其中一个实例上，两套引擎的 token 吞吐相加。双实例减少了四卡跨 NUMA 的张量并行通信，但会增加模型副本、路由及运维复杂度。本次数字只适用于所测模型、输入输出长度和短时突发，长上下文、不同提示分布及持续流量仍需另测。

## 前端 Chat 验收

在现有单套 TP4/64 部署上，用真实 Chromium 经 Nginx → Chainlit → LiteLLM → vLLM 测试。每个并发会话使用独立登录用户；计时从点击发送到 DOM 首次出现模型正文，包含应用排队和本机浏览器渲染，不包含外部网络。并发请求平均输出约 549–551 token；单会话短问题平均输出约 44 token，因此不同组也不是完全相同的工作量。

| 浏览器会话数 | 成功 | 平均首字 s | p95 首字 s | 平均整次耗时 s | 出现排队提示 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1（连续 3 次） | 3/3 | 0.334 | 0.500 | 1.66 | 0 |
| 16 | 16/16 | 3.903 | 4.087 | 26.77 | 0 |
| 64 | 64/64 | 9.861 | 10.160 | 57.73 | 0 |
| 100 | 100/100 | 30.138 | 64.591 | 74.79 | 31 |

四组共 183 个请求全部完成，均观察到增量渲染、额度结算与可见用量更新，生成期间无页面 JavaScript 异常、HTTP 5xx、renderer crash、意外导航或 WebSocket 关闭。100 会话组约 0.169 秒内提交，峰值超过当前 64 的全局 admission 限额，因此部分页面排队；不能用 64 会话组的 10 秒首字推断 100 会话的体验。浏览器与模型运行在同一服务器，100 个 Chromium 页面带来的 CPU 争用也计入延迟。

额外验收通过：同一线程连续两轮对话，第二轮正确复述第一轮的校验码，两个回答均留在页面且逐字更新；停止后预留归零和继续聊天；生成中刷新后正文从 119 字增长至 263 字，停止按钮恢复并可再次停止；模拟 `/chat/user` 重校验连接失败后保持登录，恢复后请求返回 200；复制按钮正常。最终账本 `reserved` 记录为 0，用户和线程预留总量均为 0，vLLM 运行/等待请求均为 0。

完整验收成功后，服务器 `infra/env/host.env` 的 `MAX_NUM_SEQS` 保留为 64，`TP_SIZE=4`，Chainlit 全局 admission 默认随之为 64。模板仍以 32 为保守初始值，其他机器应重新测量。
